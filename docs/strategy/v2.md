# v2 — 공격형 (궤적 예측 + 파워히트 탐색)

> `src/code-here/LuckyPunch_v2.js` · 386줄 · 오프라인 종합 승률 **79.7%**
> ⚠️ **정지 구간 버그 있음** — 브라우저 실전에서는 서브를 통째로 놓친다 (v3에서 수정)

## 한 줄 요약

엔진 물리(`physics.js`)를 봇 안에 그대로 복제해서 **미래를 계산한다.**
공의 궤적을 프레임 단위로 예측하고, 점프 타이밍을 역산하고, 파워히트 6조합을
전부 시뮬레이션해 상대가 못 따라올 곳으로 보낸다.

21.9% → 79.7%. 이 프로젝트에서 가장 큰 도약이다.

## 핵심 아이디어 — 엔진 복제

내장 AI의 `expectedLandingPointXWhenPowerHit`는 네트 충돌 판정을 **일부러 틀리게**
짜 놓았다 (원본 주석: *"make computer do mistakes"*). 우리가 정확한 판정을 쓰면
그만큼 순수한 우위가 된다.

`stepBall(b)` — physics.js의 `processCollisionBetweenBallAndWorldAndSetBallPosition`과
**같은 순서**로 1프레임을 굴린다:

```
1. x + vx 가 0 미만이거나 432 초과 → vx 반전
2. y + vy < 0 → vy = 1
3. 네트 기둥 (|x-216| < 25 && y > 176)
     y <= 192 → vy > 0 이면 반전
     아니면   → vx를 바깥쪽으로
4. y + vy > 252 → 착지 (이 프레임엔 x를 더하지 않는다 — 엔진과 동일)
   아니면       → y += vy; x += vx; vy += 1
```

4번의 "착지 프레임엔 x를 더하지 않는다"까지 맞춰야 낙하지점이 엔진과 일치한다.

## 3단 파이프라인

### 1단계 — 궤적 예측

`predictTrajectory(ball)` → `traj[f]` = f프레임 뒤의 `{x, y, vy}`. 착지하면 멈춘다.
최대 150프레임.

### 2단계 — 점프 타이밍 역산

점프 물리는 결정론적이다: 입력 프레임에 `yVelocity = -16`, 매 프레임 `y += v` 후 `v += 1`.
그래서 테이블로 미리 굽는다.

```js
JUMP_Y[n] = 점프 입력 n프레임 뒤의 플레이어 y   // 정점 n=16 → y=108, 총 33프레임
```

계획은 이중 루프로 역산한다:

```
프레임 g에 공을 만나려면  →  프레임 g-k 에 점프해야 한다  (JUMP_Y[k] ≈ traj[g].y)
```

- `g`를 **작은 것부터** 본다 → 닿을 수 있는 **가장 이른(=가장 높은) 접촉**을 고른다
- `q.y > MIN_SMASH_HEIGHT(210)` 이면 스킵 — 너무 낮아서 점프해봐야 착지 중에 지나간다
- `|target - myX| > 6 * (g - lag) + 32` 이면 스킵 — 그 프레임까지 못 간다
- `jumpAt < lag` 이면 스킵 — 이미 늦었다, 더 늦은 접촉을 찾는다

이 tick의 입력은 lag 프레임 뒤부터 3프레임 유지되므로, `jumpAt <= lag + 2`면 **지금** 점프한다.

### 3단계 — 파워히트 조합 탐색

접촉 순간의 공 상태로 **7가지 수**를 전부 시뮬레이션한다.

파워히트 물리 (`powerHitVelocity`):

```
vx = (공이 네트 왼쪽) ? +(|입력x|+1)*10 : -(|입력x|+1)*10
vy = max(|공의 vy|, 15) * 입력y * 2
```

**여기가 자주 틀리는 곳이다.** 파워히트 방향은 내 입력 `x`의 부호가 아니라
**공이 네트 어느 쪽에 있느냐**로 결정된다. `|x|`는 속도 배율일 뿐 (0→10, 1→20).

| 조합 | 결과 |
|---|---|
| `\|x\|` ∈ {0, 1} | 속도 10 또는 20 |
| `y = -1` | 아치 (못박기) |
| `y = 0` | vy가 **정확히 0** — 수평 직선 |
| `y = 1` | 최소 30으로 하강 — 강스매시 |
| + 몸통 리턴 | `vx = (공x-내x)/3`, `vy = -max(\|vy\|,15)` |

6조합 + 몸통 리턴 = 7개를 `simulateLanding`으로 굴려 점수를 매긴다:

```js
scoreLanding = |낙하x - 상대x| - 6 * 도달프레임
```

상대는 프레임당 6px 움직인다. 그래서 "거리 − 6×시간"이 곧 상대가 못 따라오는 여유다.
상대 코트에 못 꽂으면 `-1000` (자책골).

몸통 리턴에는 `BODY_RETURN_BIAS = 12` 감점 — 동점이면 파워히트를 선호한다.

## 다이빙 폴백

점프 스매시가 안 되고 걸어서도 못 닿을 때:

```js
if (gap > 6*framesLeft && gap < 6*framesLeft + 48 && ball.y > 176)
  return { x: 방향, y: 0, hit: 1 };   // 지상 + x≠0 + hit=1 = 다이빙 (8px/frame)
```

`hit=1`이 항상 파워히트인 게 아니다. **지상 + `x≠0` + `hit=1` = 다이빙.**

## v2의 치명적 결함 — 정지 구간

득점 후 게임은 `afterEndOfRound`(5프레임) → `beforeStartOfNextRound`(30프레임) 동안
**physics를 돌리지 않는다.** 첫 랠리는 `startOfNewGame`(71프레임). 그런데 `decide`는
그 사이에도 계속 호출된다.

v2는 그 **얼어붙은 스냅샷**을 보고 "지금 점프"라고 답한다. 그 입력이 랠리 첫 프레임에
그대로 적용되어 **공이 오기 30프레임 전에 점프**해버린다. 점프는 33프레임이면 끝나므로
공이 도착할 땐 이미 착지해 있다 → **서브를 통째로 놓친다.**

오프라인 하네스에서 79.7%였던 봇이 브라우저에서 5-10으로 졌다.
(하네스가 정지 구간을 재현하지 않았던 탓 — 이후 하네스도 고쳤다.)

→ v3에서 수정.
