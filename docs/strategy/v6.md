# v6 — 커밋 겨냥 공격

> `src/code-here/LuckyPunch_v6.js` · 상대 풀(AI·v1~v4) 종합 **92.6%** · **v5와 맞대결 50%**
> 수비는 v5의 예측 수비를 그대로 쓴다. 바뀐 건 **공격 채점 하나**다.

## 한 줄 요약

v5까지의 공격 채점은 수비수를 **전지적**으로 가정했다. v6는 그걸
**"상대는 이미 어딘가로 걸어가는 중이고, 내 타격을 보고 나서야 방향을 바꾼다"** 로 바꾼다.

**목표였던 "v5를 이긴다"는 실패했다** (맞대결 50%). 다만 상대 풀 종합에서는 동급~미세
우위라 제출 후보 자격은 유지했다. 그리고 **이 버전의 진짜 산출물은 측정 프로토콜 교훈**이다.

## 문제 — 전지적 수비수 가정

v5의 `evaluateShot`은 상대의 도달 범위를 이렇게 쟀다:

```js
var reach = PLAYER_SPEED * (t + headStart);   // 내 결정 순간부터 최적 이동 시작
```

즉 **내가 결정을 내리는 순간부터 상대가 최종 낙하점을 향해 최적으로 달리기 시작한다**고
본다. 이건 상대에게 두 가지 초능력을 주는 것이다:

1. **내가 아직 치지도 않은 공의 착지점을 이미 안다**
2. **반응 지연이 0이다** — 내 타격을 보자마자 방향을 튼다

이 최악 가정에서도 못 닿는 공만 킬로 인정하니, **대부분의 옵션이 "닿을 수 있음"으로
기각된다.** 실제로는 들어갔을 공을 놓치는 것이다.

## 해결 — 커밋 + 반응 모델

실제 수비수는 그렇게 못 움직인다:

1. **이미 어딘가로 걸어가는 중이다** (커밋). v5의 예측 수비조차 maximin 위치로
   미리 걸어가는 커밋이다 — 자기가 하는 짓을 상대는 안 한다고 가정한 셈이다.
2. **내 타격을 보고 나서야** 방향을 바꾸고, 그 반응에도 ~1 tick이 걸린다.

### (a) 상대 위치 외삽 — `predictOppX`

먼저 상대 속도를 추적한다. `decide`는 3프레임마다 호출되므로 3으로 나눈다.

```js
if (!frozen && prevOppX >= 0) {
  var dv = (s.opp.x - prevOppX) / 3;
  oppVelPerFrame = clamp(dv, -PLAYER_SPEED, PLAYER_SPEED);
} else {
  oppVelPerFrame = 0;      // 정지 구간에선 위치가 안 변한다 → 갱신 금지
}
```

그리고 **내 타격이 일어날 시점**의 상대 위치를 외삽한다:

```js
function predictOppX(oppX, frames, oppOnRight) {
  return clamp(oppX + oppVelPerFrame * frames, lo, hi);   // 코트 밖으론 못 나감
}
```

### (b) 반응 지연 — `OPP_REACT = 4`

```js
// v5:  reach = 6 * (t + headStart)
var reach = PLAYER_SPEED * Math.max(0, t - OPP_REACT);
var canLo = Math.max(oppReachMin, pHat - reach);
var canHi = Math.min(oppReachMax, pHat + reach);
```

`OPP_REACT = 4`는 **결정 주기 1 tick(3프레임) + 반영 1프레임**이다. 타격 후 4프레임
동안 상대는 `pHat`에 **묶여 있다**고 본다.

낙하 항에도 같은 보정이 들어간다:

```js
var landingTerm = Math.abs(shot.landingX - oppX)
                - PLAYER_SPEED * Math.max(0, shot.frames - OPP_REACT);
```

### (c) 인자 교체

`headStart`(상대가 이미 움직일 수 있었던 프레임 수)가 사라지고 `pHat`(상대의 예상
위치)이 그 자리를 받는다. 호출부가 전부 바뀐다:

```js
chooseHit(c.x, c.y, c.vy, myX, isLeft, predictOppX(oppX, contact, isLeft))
```

**의미가 뒤집혔다.** v5는 "상대에게 시간을 얼마나 줬는가"를 감점했고, v6는
**"상대가 그때 어디 있을 것인가"** 를 직접 겨냥한다. 즉 **상대가 실제로 있을 곳의
반대편**을 노린다.

## 솔직한 성적표

최종 (lag1, 지터 {0, 8}, 상대당 48게임):

| | vs AI | vs v1 | vs v2 | vs v3 | vs v4 | vs v5 | 풀 평균* |
|---|---|---|---|---|---|---|---|
| v5 | 83% | 83% | 85% | 100% | 100% | — | 90.2% |
| **v6** | 90% | 94% | 83% | 98% | 98% | **50%** | **92.6%** |

\* 풀 평균은 **집안 맞대결(vs v5)을 제외한** AI·v1~v4 5종의 평균이다.

AI·v1 상대로는 확실히 늘었다 (83→90, 83→94). 하지만 **v5와는 정확히 50%.**

## 이 버전의 진짜 산출물 — 측정 교훈 셋

### 1. 집안 맞대결은 신호가 거의 없다

v5-v6 랠리 로그를 프레임 단위로 까보니, 특정 진영 조합에선 **33랠리 전부
"서브 넣은 쪽이 승리"** 였다. 세트 승부가 사실상 **순수 서브 추첨**이다.

초기에 "vs v5 73~95%"라고 보고했던 수치는 **지터·시드 운이 만든 허수**였다.
비슷한 실력의 봇끼리는 랠리가 짧게 끝나고, 그 짧은 랠리를 서브권이 결정한다.

### 2. `CONTACT_GAIN = 15` 실험은 회귀였다

v4에서 정한 60을 낮춰봤다. **특정 시드에서 v5 상대 성적이 좋아 보였지만**,
상대 풀 종합에서는 **72.5%로 크게 후퇴**했다. 60으로 복원했다.

이건 v4에서 이미 배운 것(`CONTACT_GAIN`은 지연 환경에 거는 도박)의 반복인데,
**소표본에 속아 같은 실수를 한 번 더 했다.**

### 3. 측정 프로토콜 — 이게 결론이다

> **상대 풀 종합(지터 {0,8} × 시드 24개 × 양 진영)이 아니면 믿지 말 것.**
> 소표본 단일 조건 수치는 **±20%p씩 튄다.**

v6 이후의 모든 수치는 이 프로토콜로 다시 쟀다. v1~v5 문서의 옛 수치들과 절대값이
다른 이유이기도 하다.

## 남은 것

공격 모델을 고쳤는데도 v5를 못 이겼다는 건, **승부가 갈리는 지점이 공격 채점이 아닌
다른 데 있다**는 뜻이다. v7에서 그 지점을 찾는다 — 공중에서의 낙하점 추적 버그였다.

그리고 v6가 "상대 위치·속도를 외삽해 겨냥할 수 있다"를 증명했다는 건,
**우리도 똑같이 당할 수 있다**는 뜻이다. 이것도 v7이 받는다.
