# v5 — 예측 수비 (maximin)

> `src/code-here/LuckyPunch_v05.js` · 811줄 · ~~현재 주력~~ → **[v10](v10.md)으로 교체됨**
> 실측 지연에서 v4 상대 **100%** · 브라우저 실전 v4에 **10-3, 10-2** 승

## 한 줄 요약

공격은 v4와 동일. **수비를 통째로 바꿨다.**
공이 상대 쪽에 있을 때 상대의 접촉 시점을 추정하고, 그가 둘 수 있는 **7가지 수의 낙하
지점**을 전부 시뮬레이션해서, **가장 받기 어려운 수까지의 부족 거리가 최소가 되는 위치**
(maximin)에 미리 가서 선다.

## 왜 수비인가 — 미러전 관찰

v4끼리의 랠리를 프레임 단위로 추적하면 거의 항상 **3타 교환**으로 끝난다:

```
서버 스매시 → 수비자 공중 요격·반격 → 서버 재반격 → 득점
```

승부는 결국 **"재반격이 꽂힐 때 수비자가 어디 서 있었는가"** 하나로 갈린다.
v4의 수비는 코트 중앙 고정 대기라 여기서 진다. 공격을 더 다듬는 것보다
**수비 위치 하나를 고치는 게 훨씬 크다.**

## `planDefense()` — 3단계

### 1) 상대의 접촉 시점 추정

상대 코트에서, 상대가 도달 가능하고(`|q.x - oppX| <= 6g + 32`), 스매시 가능한
높이(`q.y <= 210`)에 공이 있는 **가장 이른 프레임**.

v4류는 가장 이른 접촉을 고르므로 이 추정이 실제와 거의 일치한다.

### 2) 위협 목록 = 7가지 수의 **낙하 지점**

```js
for (xMag of [0,1]) for (yDir of [-1,0,1]) {
  v = powerHitVelocity(c.x, c.vy, xMag, yDir);
  → stepBall 반복 → { landX, flight }
}
+ 몸통 리턴 (vx=0, vy=-max(|c.vy|,15))   // 내장 AI·수비형 봇이 자주 쓰는 수
```

**내 코트에 떨어지는 것만** 위협으로 센다 (상대 자기 코트행·네트행은 상대의 자책골).

> **핵심 교훈:** 위협 커버리지를 "비행 중 요격 가능성"으로 재면 **과대평가**가 된다.
> 공중 요격은 점프 선행 프레임이 필요해서 실제로는 거의 못 잡는다 (측정으로 확인).
> 믿을 수 있는 수비는 **낙하 지점 선점**뿐이다 → 위협을 낙하 지점으로 요약해야 작동한다.
>
> v3의 `evaluateShot`(공격 평가)이 비행 전 구간을 보는 것과 **대칭이 아니다.**
> 공격 평가에서는 "상대가 손댈 가능성"을 비관적으로 세는 게 맞고,
> 수비 계획에서는 "내가 실제로 잡을 수 있는가"를 낙관하면 안 된다.

### 3) maximin

```js
margin(위협, p) = |낙하x - p| - 6 * 비행프레임 - 32     // 양수 = 제때 못 감
worst(p)        = max over 위협  margin
defenseX        = argmin over p  worst(p)
```

후보 `p`는 `reachMin`부터 `reachMax`까지 **8px 간격**, 단 **접촉 전까지 실제로 도달
가능한 곳만** (`|p - myX| <= 6*avail + WALK_DEADBAND`).

> **후보 제한이 필수다.** 제한을 풀면 이론상 좋아 보여도 접촉이 임박했을 때
> 목표가 튀어 다니며 손해를 본다.

동률(±1px)이면 **코트 중앙에 가까운 쪽** — 다음 전개에 중립적이다.

### 왜 maximin이 옳은가

상대가 "내 위치에서 가장 먼 곳"을 노리는 봇(= v4류, 그리고 대부분의 공격 봇)이라면,
**maximin이 정확한 최적 대응**이다. 다른 봇이라도 위협 집합 전체를 커버하는 위치라
손해가 없다.

## 신뢰도 조절 — `DEF_GROUND_TRUST`

```js
trust = (opp.state === 1 || opp.state === 2) ? 1 : DEF_GROUND_TRUST;
defenseX = standbyX + trust * (plan.x - standbyX);
```

상대가 **점프 중(state 1·2)** 이면 공격 확정 신호다 — 접촉점과 위협 집합이 거의 그대로
실현되므로 예측을 전량 반영한다. 지상의 상대는 자유도가 커서 예측이 자주 빗나간다.

`DEF_GROUND_TRUST = 1` (전량 반영)로 확정했다.

| 지연 | 결과 |
|---|---|
| **1 (브라우저 실측)** | 전 상대 최소 75%, v3·v4 상대 100% |
| 2 | 약한 상대에게 뒤집힘 (21~25%) — **트레이드오프** |

**반영 지연 1은 브라우저에서 직접 계측한 값**(`pendingRequestId` 전이 추적)이라
lag1 성능을 우선했다.

> ⚠️ **대회 당일 지연이 2로 보이면 재검토할 것.** 그 경우 v4가 안전판이다.

## 시도했으나 끈 것 — `DEF_AIR = 0`

"공중에서 더 못 칠 공(상대 코트로 떠나감)은 쫓지 않고 즉시 수비 위치로 복귀"를
구현했지만, 예측 수비와 조합하면 **네트 근처 커버를 버리는 셈이라 순손해**였다.

다만 그 과정에서 발견한 **버그 수정은 유지했다**:

```js
if (isLeft ? q.x >= NET_X : q.x <= NET_X) continue;  // 상대 코트의 공은 접촉 후보가 아니다
```

v4는 떠나가는 공에도 x·y가 우연히 맞는 프레임이 있어 `contact >= 0`이 되고,
`onMySideAtContact` 체크만 실패한 뒤 맨 아래의 "공 추적"으로 떨어졌다.
그래서 반격 직후 공을 따라 네트까지 가버렸다.

## 신규 파라미터

| 이름 | 값 | 의미 |
|---|---|---|
| `DEF_PREDICT` | 1 | 1이면 maximin 예측 수비, 0이면 v4처럼 중앙 대기 |
| `DEF_GROUND_TRUST` | 1 | 상대가 지상일 때 예측을 얼마나 믿을지 (0=중앙, 1=전량) |
| `DEF_AIR` | 0 | 공중 수비 복귀 — 측정 결과 손해라 OFF |
